## 一、成员 1：控制面（`round_runner` 等）

1. **【高·实测】整轮没有任何出错兜底。** 成员 2–5 任何一步抛异常，这一轮都会直接崩溃，而且不调用 `finish`。平台上这一轮就算失败，「十轮无人干预」也就断了。会触发的情况包括：
   - 训练失败；
   - CPU 预算用完（`BudgetExceeded`）；
   - 自适应搜索的所有计划都失败；
   - Qwen 调用失败；
   - 回滚出错（我实测复现了三种）。

   建议：除了 SDK 自己的 `HarnessError`，其余异常全部捕获；保留父模型，确保至少有一次模型调用，照常 `finish`，并记下失败原因。
2. **【高·实测】成员 5 的每轮记录在平台上会丢。** 这些记录写在 `/workspace/records`，没有存进状态。SDK 规定 `/workspace` 是「本轮工作目录」，每轮都会清空，所以平台跑完以后拿不到。我在合并后的代码上跑了 C 的 10 轮，最终状态里只有成员 5 的指标文件，没有轮次记录。成员 5 README 里「把 `/workspace/records` 导出到开发机」这一步，在平台上做不到。建议把每轮的精简记录追加写进状态里的一个 jsonl 文件，或者写进 `finish` 的 `configuration`（上限 64 KiB）。
3. **【中】完全没有时间控制。** 代码不读 `rnd.limits`，也不会根据剩余时间缩小训练规模。目前 C 一轮训练加门控只要几秒 CPU，风险不大；但 B 的剪枝和多候选在 2 核机器上要跑多久，没人测过。
4. **【中·实测】预测时每条样本都重新加载模型。**

   | | 每条耗时（重新加载） | 每条耗时（缓存模型） | 跑完整个验证集 |
   |---|---:|---:|---|
   | A | 2.38 ms | 0.38 ms | |
   | C | 1.96 ms | 0.10 ms | 23,049 条：45 秒 vs 2 秒 |

   平台只有 2 核，会更慢。建议按模型文件路径缓存预测器。
5. **【中】实验记录里的「假设」是一大段原始 JSON。** `submit_candidate` 和 `finish` 的 `hypothesis` 字段直接放了成员 2 的 notes，最多约 3.9 KB。平台的实验记录和专家评审看到的就是这串 JSON。建议写一句人能读懂的假设，再附几个关键数字。
6. **【低】没有读取平台的测量结果。** `submit_candidate` 会返回平台测量的验证摘要（SDK 说「分数以返回值为准」），但代码没有读取，也没有记录。
7. **【低】容器不响应停止信号。** Dockerfile 没有处理 SIGTERM：Python 作为 1 号进程时会忽略它，平台超时后只能强杀（退出码 137），诊断信息容易被误读。
8. **【低·实测】本地模拟宿主有缺陷（成员 1/5 的测试基础设施）。** 每次提交候选，它都返回同一个产物 ID `model-2`；多轮运行时，历史产物列表永远是空的。后果有两个：
   - 多轮回滚根本测不到；
   - 验收会误报「上线却选了父产物」。在成员 5 的分支上跑 C 的 10 轮，有 5 轮因此被判失败。

## 四、成员 4：工业模型训练

1. **【中】epoch 上限写死，太低。** A 最多 5 个 epoch，C 最多 2 个，决策里传更大的值也改不了。对照实验里，A 的平均 F1 是 0.926，固定 20 轮 finetune 是 0.951。上次 PR 里已经提过，main 还没改。
2. **【中】「最近 X%」窗口取的是训练文件末尾的行。** 这默认了新数据排在文件最后，但平台的 `/data/train.jsonl` 不保证行的顺序。成员 1 已经把哪些行是新的标出来了（`new_rows`），训练器只用它算了个占比，没用来选窗口。
3. **【中】剪枝可能被判不合规。** 结构化剪枝把隐藏层宽度从 baseline 剪到 8。权重是从父模型迁移的，形式上算续训；但 v1 刚被平台标了「不得从头训练另一套模型替代 baseline」，改模型结构是否合规，建议先问组委会。另外剪枝只在一个公开切分上验证过，队长已经列了这一点。
4. **【中】失败时直接让整轮崩溃。** 自适应搜索的所有计划都失败时抛 `TrainingError`，预算用完时抛 `BudgetExceeded`。和一·1 是同一个问题。

## 五、成员 5：门控、记录与验收

1. **【高·实测】历史产物回滚（`57cc6ea`）有三个问题。**
   - 会选回更差的模型：恢复的旧模型在本轮验证集上 F1 只有 0.292，父模型是 0.714，系统照样选用了它。
   - 会选中从没上线过的产物，比如当年被门控拒掉的候选。
   - 出错时整轮崩溃、不调用 `finish`：目标模型和任务不匹配、下载文件损坏、按哈希回滚但有重复哈希，三种情况我都复现了。

   建议：回滚前把恢复的模型在本轮验证集上过一遍门控；只允许回滚到曾经被选中过的产物；出错就保留父模型。
2. **【高·实测】README 推荐的验收命令永远过不了。** 离线验收工具检查的是「决策动作」，而 `--require-action promote` 里的 promote 是门控结果，不是决策动作。我实测：10 轮里上线 6 次、门控拒绝 4 次，三项仍然全部报「没有观察到」。
3. **【中·实测】次要指标的容差是绝对值 0.02，回归任务几乎不可能通过。** 只要 MAE 变差超过 0.02 就拒绝，哪怕 RMSE 改善了 50（我实测了这个例子，结果是拒绝）。B 的 RMSE 有几百（分钟），这个门槛等于「MAE 一点都不许变差」。建议改成相对容差，比如 1%。
4. **【中】「rollback」一个词有两个意思。** 门控拒绝候选时也写 `rollback`，和主动恢复历史产物混在一起，历史记录里分不清。
5. **【中·实测】两折稳健性审计挡不住验证集和隐藏集之间的差异。** 它是把同一份验证集切成两半。C 第 9 轮两折都在提升（+6.97、+5.50），被标为 robust，但隐藏集 RMSE 从 87.2 变成了 88.9。可以继续记录，但不能把它当成「上线一定对」的证明。
6. **【中】提交号的处理有两个问题。**
   - 不在 git 仓库里跑测试时（比如从压缩包解出来），回滚测试会因为拿不到提交号而失败。
   - 镜像默认值 `unknown` 会被当成有效提交号。
7. **【中】改了别人负责的文件。** 成员 5 的分支直接改了成员 1 的 `round_runner` 和成员 3 的 `decider`，三·2 的版本冲突就是这么来的。
