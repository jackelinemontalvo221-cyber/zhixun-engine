一、这项比赛到底在做什么
========================

比赛名称：
第二届北京市大学生“人工智能 +”创新大赛

赛题名称：
“智训引擎”——工业制造场景下的模型训练与超参数优化

赛题提供方：
软通计算机有限公司、华为技术有限公司

核心问题：
工业设备长期运行时，传感器数据、工况和输入输出关系会随时间变化，
导致模型发生数据漂移和性能退化。传统“一次训练、长期使用”的静态模型
会逐渐误报、漏报或质检失效。

本赛题要求参赛队开发一个“工业模型自进化系统”。系统不能只提交一个
训练好的高分模型，而要提交 Harness、模型配置、工业模型和完整运行机制。
它要在没有人工干预的情况下接收连续的隐藏测试阶段，自动完成：

    接收数据
    -> 监测漂移
    -> 分析原因
    -> 提出实验
    -> 训练或调整工业模型
    -> 比较旧模型与候选模型
    -> 决定上线、保持或回滚
    -> 记录证据
    -> 接收下一批数据

本项目关注的是“模型层自迭代 + 策略层自改进”的受控 RSI
（Recursive Self-Improvement，递归自我改进）机制，但必须可控、
可验证、可追溯、可回滚，不允许无限自动迭代。

四、团队分工截图内容
====================

整条流水线：

    成员 1 数据入口
    -> 成员 2 诊断报告
    -> 成员 3 决定
    -> 成员 4 候选模型
    -> 成员 5 评测、上线、记录
    -> 成员 1 接收下一批数据

成员 1，负责步骤 1、2、3、13 和 Docker 打包：
- 模块：数据入口与主循环；
- 接收数据、校验、计算哈希；
- 把本轮数据交给后续成员；
- 接收最终决定；
- 获取下一批数据；
- 最后打包镜像；
- 对外交付一份干净的“本批数据”。

成员 2，负责步骤 4：
- 模块：漂移分析与预算；
- 判断数据是否变化、如何变化；
- 统计剩余算力和 Token；
- 在大模型接入前先写一套临时决策规则；
- 对外交付一份“诊断报告”。

成员 3，负责步骤 5、6、7：
- 模块：大模型决策；
- 将诊断报告写成 Prompt 发给大模型；
- 取回决定并检查决定是否合法；
- 对外交付一个“决定”。

成员 4，负责步骤 8、9：
- 模块：训练与候选；
- 按照决定训练工业模型；
- 产出候选版本；
- 支持气体、轴承、发动机三类任务；
- 对外交付一个“候选模型”。

成员 5，负责步骤 10、11、12：
- 模块：评测、上线和记录；
- 比较候选模型与旧模型；
- 决定上线或回滚；
- 将本轮过程写入 SwanLab；
- 对外交付一条“本轮记录”。

图片强调：
每个人只需要关心自己收到什么、交出什么。

第一天需要共同确定的四个格式：
1. 诊断报告，成员 2 -> 成员 3：
   漂移分数、漂移类型、当前成绩、剩余预算；
2. 决定，成员 3 -> 成员 4：
   动作（不更新、重训、微调、回滚）、参数、理由；
3. 候选模型，成员 4 -> 成员 5：
   统一预测函数和保存方式；
4. 记录模板，成员 5 输出，所有人照此填写。

开工顺序：
1. 成员 1 先搭主循环空架子，每一步先放最简单的占位代码；
2. 成员 4 接上“每批全量重训”，成员 5 接上评测和 SwanLab，
   先让保底版本跑通；
3. 成员 2 补上漂移分析和临时规则；
4. 成员 3 接上大模型决策，替换临时规则。


五、比赛对最终运行环境的要求
============================

根据对话和图片，可以确定：
- 最终评测环境没有 GPU；
- 工业模型必须在 CPU 环境续训和预测；
- 正式评测环境断网，不能依赖外部模型或 API；
- Harness 驱动模型必须满足组委会规定来源；
- 数据和标签由平台在运行时释放，隐藏测试标签不可见；
- 系统必须无人干预完成全部阶段；
- 模型必须可回滚，不能无条件覆盖上一版本；
- 需要至少 3 次完整“读历史 -> 提假设 -> 做实验 -> 做决策”证据；
- 需要记录资源、实验、指标、候选模型和决策；
- 最终交付 Docker 系统镜像和完整复现材料。

因此，开发时不能把“Windows 本机能跑”当成完成标准。应在 Linux
容器中测试路径、权限、文件写入、信号处理、依赖和 CPU 资源限制。


六、三个数据包分别在做什么
==========================

当前工作区有三个比赛包：

1. cpu-a-guide-20261110-v1

任务：
气体传感器漂移下的六类气体识别。

输入：
每次气体测量有 128 个数值特征。

类别：
Ethanol、Ethylene、Ammonia、Acetaldehyde、Acetone、Toluene。

指标：
主指标 Macro-F1，辅助 Accuracy、混淆矩阵。

数据来源：
UCI Gas Sensor Array Drift 数据集。

公开数据：
- public/train.jsonl；
- public/validation.jsonl。

基线：
NumPy MLP，128 输入、32 个 tanh 隐藏单元、6 类 softmax。

已知结果：
- Accuracy 约 0.8786；
- Macro-F1 约 0.7140；
- Acetaldehyde 容易与 Ethanol 混淆；
- 跨批次漂移明显。

A 最适合作为完整 Harness 主循环的第一套开发样板，因为 UCI 原始数据
有 batch1.dat 到 batch10.dat，可以直接模拟十阶段数据流。

2. cpu-b-rul-20261110-v1

任务：
滚动轴承剩余寿命预测。

输入：
水平和垂直两个通道，每通道 17 个特征，共 34 个特征。

目标：
当前快照距离该轴承最后记录时刻的剩余寿命，单位为分钟。

指标：
RMSE、MAE，越低越好。

数据来源：
XJTU-SY 完整运行至失效记录。

公开数据：
- public/train.jsonl；
- public/validation.jsonl。

分组规则：
训练、验证、隐藏测试按整根轴承分开，同一根轴承的时间片不能跨集合。

已知基线：
- RMSE 约 681.16；
- MAE 约 563.11；
- 模型存在明显回归均值现象；
- 历史最佳公开结果出现在中间轮次，最终检查点不一定最佳。

B 的误差大并不代表数据没有价值。它提示检查点选择、门控和回滚很关键。

3. cpu-c-guide-20261110-v1

任务：
涡扇发动机剩余寿命预测。

输入：
3 项运行设置和 21 项传感器数值，共 24 个特征。

目标：
发动机当前循环后的剩余运行循环数，单位 cycles。

指标：
主指标 RMSE，辅助 MAE，另看 NASA 非对称评分。

数据来源：
NASA C-MAPSS，包含 FD001 至 FD004。

公开数据：
- public/train.jsonl；
- public/validation.jsonl。

分组规则：
按整台发动机分割，不把同一台发动机拆到训练和验证。

已知基线：
- RMSE 约 52.87；
- MAE 约 38.90；
- 低 RUL 容易高估，高 RUL 容易低估；
- FD003、FD004 通常更难。


七、每个比赛包中的文件是做什么的
================================

START.md：
包的入口说明，告诉使用者先看 TASK 和 TRAINING_GUIDE。

TASK.md：
定义任务输入、标签如何生成、允许输入、评价指标和续训要求。

TRAINING_GUIDE.md：
说明如何从基线检查点开始训练、如何续训、输出目录规则、
数据隔离要求以及每轮结果应检查什么。

training.json：
记录基线训练元数据，包括：
- profile、任务类型、是否适合正式评分；
- CPU、Python、NumPy 版本；
- stage_id、随机种子、参数量；
- 训练和验证样本数；
- 文件 SHA256；
- 父检查点和当前检查点 SHA256；
- 初始和最终步数；
- 验证前后指标；
- 网络结构、学习率、批大小和标准化方案。

history.jsonl：
逐 epoch 保存训练损失、验证指标、阶段和种子。

checkpoint.npz：
保存模型权重、Adam 状态、累计步数、随机种子、输入标准化状态、
目标缩放和任务 schema 等。

public/train.jsonl：
公开训练样本和目标。

public/validation.jsonl：
公开验证样本和目标，用于比较改动，不能并回训练集。

baselines/data.py：
读取和校验 JSONL，展开不同任务的特征路径。

baselines/model.py：
小型 NumPy MLP、损失、预测、检查点加载和保存逻辑。

baselines/train.py：
训练和续训入口，生成 checkpoint、training.json、history.jsonl。

baselines/predict.py：
按统一预测协议输出分类分数或回归值。

baselines/configs/A.json、B.json、C.json：
三种任务的模型和数据结构配置。

baselines/tests/test_baselines.py：
测试数据读取、训练、续训、预测和打包行为。

因此，三个包本身只有公开训练集、验证集、基线代码和历史检查点，
没有正式的阶段流、隐藏测试数据或平台运行接口。


八、对话中关于数据的结论
========================

1. 这些包是否由不同批次组成？

A 可以直接对应原始 UCI 批次。公开训练和验证数据保留批次来源，
原始数据还有 batch1 到 batch10，可以构造连续漂移阶段。

B 不能按随机时间片拆阶段。应按整根轴承分组，避免同一轴承泄漏到
训练和验证两侧。

C 应按整台发动机分组。可以按 FD001 至 FD004 构造阶段，
也可以进一步按发动机整组划分，但不能把同一发动机拆散。

2. 数据如何统一接口？

统一的是外层数据契约，不是把三个任务强行变成相同维度：

- A 使用 128 维特征和六类标签；
- B 使用 34 维特征和非负分钟目标；
- C 使用 24 维特征和非负循环目标。

内部统一为 StageBundle，建议至少包含：
- schema_version；
- task_id；
- stage_id；
- task_type；
- feature_schema_id；
- feature_uri；
- label_uri；
- label_status；
- sample_count；
- group_ids；
- feature_count；
- source_sha256；
- canonical_sha256；
- previous_stage_id；
- created_at。

模型的输入和标签必须通过任务适配器转换，不能让成员 2 到成员 5
分别实现一套文件读取逻辑。

3. 哪些字段不能作为模型输入？

- A 的 id、source_batch、source_index；
- B 的轴承编号、快照序号、总快照数；
- C 的发动机编号、循环编号、最终寿命；
- 当前 RUL 答案；
- 任何隐藏测试标签或未来观测。

这些字段可用于分组、排序、追溯和防泄漏校验，但不能输入模型。


九、完整阶段流和 stage_id 从哪里来
==================================

当前三个比赛包中没有正式隐藏阶段流，也没有 Harness 目录、
manifest、平台 SDK 或固定的阶段数据目录。

正式阶段流只能从以下位置获取：
1. 官方专属评测平台；
2. 官方数据包中的评测脚本；
3. 平台 SDK 和系统运行说明；
4. 组委会后续发布的接口文档；
5. 赛题答疑群中的正式补充通知。

包内 --stage-id 只是训练日志和检查点元数据，不是阶段数据发现机制。
例如 train.py 接收 stage_id，training.json 记录 baseline，
但训练器不会扫描目录，也不会自动获取下一批数据。

建议向组委会确认：
- 阶段目录的固定挂载路径；
- 阶段清单文件名和 JSON schema；
- stage_id 是通过命令行、环境变量、SDK、事件还是文件提供；
- 阶段数据何时完整；
- 标签是训练阶段立即可见、延迟释放还是正式评测完全隐藏；
- 下一阶段如何通知；
- 结束信号是什么；
- 超时、重试、重复 stage_id 如何处理；
- 当前模型、候选模型和最终结果写到哪里；
- CPU、内存和时间预算；
- 是否需要阶段 ack 或提交回执。

本地开发不能等待官方接口。推荐自己构造：

    stages/
      manifest.json
      stage-01/
        features.jsonl
        labels.jsonl
        profile.json
      stage-02/
        ...

本地模拟阶段：
- A：stage-01 到 stage-10 对应 UCI batch1 到 batch10；
- B：按轴承整组划分为多个阶段；
- C：FD001、FD002、FD003、FD004，或按发动机分组。

本地 features 和 labels 最好分离。Harness 只能读取当前阶段应当看到的
内容，本地评测器再读取 oracle 标签，以模拟真实平台的数据隔离。


十、成员 1 的具体职责
=====================

成员 1 的定位是：
数据入口、统一契约、主循环控制面、artifact 管理、Docker 交付。

不是简单“读文件”，也不是工业模型本身的训练算法负责人。

职责一：平台运行契约适配
- 接收 task_id、stage_id、阶段目录和平台状态；
- 为本地文件、manifest 和未来平台 SDK 做适配器；
- 不把官方路径或阶段总数写死。

职责二：数据读取和校验
- 读取 JSONL；
- 校验字段、类型、维度、有限数值、标签集合和样本 ID；
- 拒绝 NaN、Inf、重复 ID、维度错误和非法标签；
- 校验同一 group 不跨不相容集合；
- 保证隐藏标签不可见。

职责三：标准化 StageBundle
- 把 A/B/C 不同结构转成统一外层对象；
- 保留任务特有的 feature schema 和 label spec；
- 输出供成员 2 到成员 5 使用的统一对象。

职责四：哈希和证据
- source_sha256 对原始文件字节计算；
- canonical_sha256 对规范化后的特征和标签计算；
- 同一 stage_id 内容相同则复用结果；
- 同一 stage_id 内容变化则报错；
- 哈希不是加密，不能替代数据权限隔离。

职责五：驱动完整闭环

    接收 StageDescriptor
    -> 校验并规范化为 StageBundle
    -> 当前模型评估
    -> 成员 2 诊断
    -> 成员 3 决策
    -> 成员 4 训练候选
    -> 成员 5 评估、上线或回滚
    -> 原子写入 artifact
    -> 更新 active-model 指针
    -> 接收下一阶段

职责六：状态和 artifact 管理
建议状态机：
- WAITING_STAGE；
- STAGE_READY；
- VALIDATED；
- CURRENT_MODEL_EVALUATED；
- DIAGNOSED；
- EXPERIMENTING；
- CANDIDATE_EVALUATED；
- DECIDED；
- COMMITTED；
- FAILED_RECOVERABLE；
- FAILED_FATAL；
- FINISHED。

建议 artifact 结构：

    artifacts/run-001/
      stage-03.tmp-uuid/
        manifest.json
        bundle.json
        diagnosis.json
        decision.json
        evaluation.json
        candidate/
        events.jsonl
      stage-03/
      active-model.json

只有全部写入完成并关闭文件后，才把临时目录改名为正式 stage 目录。
active-model.json 也必须原子替换。

职责七：错误处理和恢复
- 文件暂时没写完：等待或重试；
- JSON/schema 错误：当前阶段失败，不训练；
- 哈希不一致：严重契约错误；
- 训练失败：拒绝候选，保留旧模型；
- 评估失败或超时：回滚本次实验；
- 资源耗尽：预算熔断；
- 平台结束：正常完成并输出总结；
- 容器收到 SIGTERM：不能破坏当前 artifact。

职责八：Docker 和 Linux 验收
- 入口使用 python -m harness.orchestrator；
- 依赖版本固定；
- CPU-only；
- 运行时不联网；
- 输入目录只读、artifact 目录可写；
- 不依赖 Windows 路径、PowerShell、CMD 或 .exe；
- 在 Linux 容器中完成最终测试。


十一、推荐接口设计
==================

StageSource：
- next() 返回 StageDescriptor 或 None；
- read(stage_id) 返回原始阶段数据；
- ack(stage_id) 在平台要求时确认处理完成。

StageCodec：
- load() 读取原始 JSONL；
- validate() 检查 schema、数值、标签和分组；
- normalize() 产生 StageBundle。

ArtifactStore：
- begin_stage() 创建临时事务目录；
- commit_stage() 原子提交；
- load_active_model() 读取当前模型；
- activate_model() 原子更新 active-model 指针。

Pipeline：
- diagnose() 调用成员 2；
- decide() 调用成员 3；
- train_candidate() 调用成员 4；
- evaluate_and_commit() 调用成员 5。

所有成员接口应满足：
- 输入对象不被修改；
- 返回结构化数据；
- 错误显式返回；
- 不直接覆盖当前模型；
- 所有实验有唯一证据 ID；
- 同一个 stage_id 具有幂等性。


十二、接口相关知识
==================

接口不等于 HTTP API。一个完整接口包括：
- 输入和输出；
- 数据 schema；
- 语义；
- 调用顺序；
- 生命周期；
- 错误分类；
- 超时和重试；
- 版本兼容；
- 权限和数据边界。

常用通信方式：
- 文件挂载：适合阶段数据、检查点和离线评测；
- CLI 参数：适合 stage-root、artifact-root 等显式配置；
- 环境变量：适合运行路径和全局限制；
- stdin/stdout：适合独立子进程；
- HTTP/SDK：只有官方提供明确在线服务时才采用。

推荐内部默认方案：
Python 函数接口 + JSON/JSONL 文件 + 文件挂载 + CLI 配置。
不要为了成员间通信额外引入 HTTP 服务。

task_id、stage_id、run_id、attempt_id 必须分开：
- task_id 表示 A/B/C；
- stage_id 表示阶段；
- run_id 表示一次 Harness 运行；
- attempt_id 表示某阶段的重试次数。

stage_id 应作为不透明字符串。不能从名字推断阶段总数、训练次数或数据身份。

幂等键建议为：

    (task_id, stage_id)

同一键已有成功结果时直接复用，不能重复训练和重复提交。

十五、Windows 与 WSL/Linux 开发说明
===================================

可以在 Windows 中编写代码，但最终必须在 Linux 中验收。

Windows 与 Linux 的主要差异：
- Windows 路径使用反斜杠和盘符，Linux 使用 /；
- Linux 文件名区分大小写；
- Linux 依赖可执行权限；
- Shell 命令不同；
- Git 行尾可能由 CRLF 变成 LF；
- Docker 停止时发送 SIGTERM；
- 文件监听、文件锁和原子改名行为不同；
- Windows Python 依赖不能直接复制给 Linux 使用。

开发要求：
- 使用 pathlib 处理路径；
- 不写死 D:\、/mnt/d 或某个官方挂载路径；
- 文件读写明确使用 UTF-8；
- 不使用 PowerShell/CMD 命令作为运行依赖；
- 不通过 shell=True 执行字符串命令；
- 使用 .gitattributes 统一 LF；
- 所有文件关闭后再做 rename；
- 不依赖 inotify 事件，优先扫描 manifest 或轮询；
- 第一版主循环尽量单进程；
- 在 WSL2 或 Docker 中运行 pytest；
- 最终使用 linux/amd64 CPU 容器、断开网络进行验收。

对话最后准备把项目数据从 Windows 复制到 WSL。当前 wsl.exe 检测结果
提示 WSL 发行版或安装状态仍需处理，因此实际复制尚未完成。

推荐迁移方式：
1. 先确认 WSL2 和 Ubuntu 发行版已安装并能启动；
2. 在 WSL 中创建项目目录，例如 ~/projects/ai-competition；
3. 不要把 D 盘路径写进代码，只把它作为复制源；
4. 大文件优先使用 WSL 内部 ext4 文件系统，而不是长期在 /mnt/d 运行；
5. 复制后在 WSL 中重新创建 Python 虚拟环境并安装 Linux 依赖；
6. 用 Linux 容器完成最终运行测试。
